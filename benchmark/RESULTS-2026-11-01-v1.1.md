# Benchmark results, 01.11.2026 (aikido v1.1: virtual shell and worker)

Two questions for v1.1.0:

1. Does the virtual shell (`tools/shell`, harness `aikido-vsh`) keep the gains of a real shell on coding tasks without host access?
2. Can `aikido agent --direct --shell --allow ...` run an ICM-structured ops worker as well as Claude Code started on the same repo?

Method and caveats: [README.md](README.md). The raw results are under `results/`, which is gitignored; the run ids are below.

## 1. Coding suite: virtual shell vs real shell vs file tools

The 12 coding tasks. The `aikido`, `aikido-bash` and `opencode` rows come from the v1.0.0 run ([RESULTS-2026-11-01.md](RESULTS-2026-11-01.md), `full-20261101-100819`). `aikido-vsh` ran later the same day (`coding-vsh-20261101-1214`), with the same models and 2 reps.

| harness | pass | median wall | tool calls | shell-shaped tasks: calls / median wall |
|---|---|---|---|---|
| aikido (file tools only) | 47/48 | 10.7 s | 646 | 300 / 23.9 s |
| aikido + real bash (host) | 47/48 | 8.6 s | 313 | 37 / 10.8 s |
| **aikido + virtual shell** | **46/48** | 10.1 s | 364 | **42 / 12.1 s** |
| opencode | 46/48 | 13.3 s | 450 | 95 / 18.4 s |

- The virtual shell gets almost all of the real shell's gain on the two shell-shaped tasks (count lines of many files, replace a host across 40 files): 42 tool calls instead of 300, without host access, through the overlay.
- Both virtual-shell failures are GLM 5.3 answering `codebase-question` wrongly. The bash harness and opencode miss the same task.
- That run exposed gaps that were fixed before the release:
  - awk failed on every call;
  - `grep -Z` and `cat -A` were missing;
  - `/tmp` did not survive between calls;
  - `<(…)` was refused.

  A rerun on Haiku after the fixes (`coding-vsh2-20261101-1325`): 23/24, median 8.8 s.
- Calls that still fail are mostly `go`, `gofmt` and `go test`, which the virtual shell does not offer by design: no compilers.

## 2. Worker suite: ICM workbooks, git, kubectl and logs, unattended

The setup:
- **Repo:** a synthetic devops worker modeled on the layout of the Wilde IT worker: L0 routing in `CLAUDE.md`, L1/L2 workbooks, component READMEs, journals, run-report template.
- **Separate repo:** a gitops repo.
- **Fake host tools:** `kubectl` with canned cluster state that refuses mutations, and a Loki-style `logcli`.
- **Real tools:** git with bare remotes.

The 4 tasks:
- an incident (crashloop, root cause OOMKilled after a deploy);
- an incident with a known pattern in the journal;
- a change on a branch of the gitops repo;
- a component sync that regenerates `inventory.md`.

Every check trusts only files, remotes and the fake tools' logs.

All harnesses use Claude Haiku 5.5:
- **claude-code:** `claude -p` with MaPa's settings, hooks and MCP switched off.
- **opencode:** `opencode run --auto` through OpenRouter.
- **aikido-worker:** `aikido agent --direct --shell --allow git --allow kubectl --allow logcli --system-file CLAUDE.md`.

Final run, same code and same day for all three harnesses (`worker-final-20261101-1414`, 3 reps):

| harness | pass | median wall | median LLM calls | cost (12 runs) | cache read tokens |
|---|---|---|---|---|---|
| **aikido-worker** | **11/12** | **50.7 s** | 13 | **$0.105** | 1.93 M |
| claude-code | 11/12 | 60.8 s | 14 | $0.164 | 4.82 M |
| opencode | 6/12 | 36.9 s | 11 | $0.083 | 2.16 M |

| task | aikido-worker | claude-code | opencode |
|---|---|---|---|
| change-memory-limit | 3/3, 38 s | 3/3, 61 s | 1/3, 36 s |
| incident-crashloop | 3/3, 53 s | 3/3, 63 s | 3/3, 60 s |
| incident-known-pattern | 2/3, 52 s | 2/3, 58 s | 1/3, 36 s |
| sync-component | 3/3, 52 s | 3/3, 61 s | 1/3, 8 s |

- aikido and Claude Code solve the same share. aikido is 17% faster by median and 36% cheaper per run. Claude Code sends about 2.5 times as many input tokens: a larger system prompt and more tools.
- Most opencode failures are runs that never pushed the worker repo.
- The one miss of aikido and Claude Code each: the run report did not cite the earlier run report with the same signature.

### How aikido got there (the order matters for reading the numbers)

**First run** (`worker-full-20261101-1214`): aikido-worker 7/12, claude-code 9/12, opencode 7/12. The transcripts showed two causes.

1. **Absolute paths.** Inside the virtual shell `/` was the workspace root. The model ran `git -C /repos/billing-gitops`, the host's git looked for a host path `/repos/...`, and the model concluded the repo was no git checkout.

   Fix: `shell.Options.MountPoint`. The CLI mounts the workspace at its real path in `--direct` mode, so the shell and host programs agree on every absolute path. Host programs also follow the shell's `cd` (`ExternalOptions.FollowWorkingDirectory`).
2. **Templates and the push.** Two run reports skipped template headings, and one run never pushed.

   Fix: the CLI's worker preamble now says "reproduce templates exactly, every heading; do the repository's completion steps and check them".

   Caveat: this preamble was written after seeing aikido's failures. The rule is generic (follow the repo's own instructions), but Claude Code and opencode got no comparable second try. Their system prompts are their own.

**Rerun** of aikido only after both fixes (`worker-aikido2-20261101-1322`): 11/12. Then the final run of all three on the same code, above.

## Caveats

- **Small numbers:** 12 runs per harness in the worker suite. A single run more or less changes the pass rate by 8 points.
- **Costs are not comparable across harnesses:** Claude Code's cost is its own `total_cost_usd`, opencode computes its own estimate, and aikido's is OpenRouter's bill.
- **Synthetic tasks:** they are modeled on real workbooks but are small. Real incidents need longer investigations, real Grafana and real clusters.
